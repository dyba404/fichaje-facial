# 2026-09-28 — Docker Desktop no arrancaba: "Virtualization support not detected"

**Síntoma → causa real → fix.** Resumen ejecutivo: el error de Docker era engañoso — la CPU tenía
virtualización activada y el hipervisor corriendo; el problema era que **WSL2 no estaba instalado**
y el instalador integrado `wsl --install` está roto en esta build de Windows. Se instaló WSL 2.7.14
con el MSI oficial de GitHub + reinicio, y Docker quedó funcionando.

## Contexto

- Máquina: Dell G15 5535, AMD Ryzen 7 7840HS, **Windows 11 Pro build 26200** (25H2).
- Motivación: contenedor Postgres+pgvector para el change 0001 del proyecto Sfr.
- Docker Desktop 29.8.0 (backend WSL2, `"WslEngineEnabled": true` en `%APPDATA%\Docker\settings-store.json`).

## Síntoma

Docker Desktop mostraba pantalla de error:

> **Virtualization support not detected**
> Docker Desktop failed to start because virtualisation support wasn't detected.
> Sign in to try restoring access to Docker features.

Engine en rojo ("Engine stopped"), RAM/CPU en 0.

## Diagnóstico (comandos y salidas reales)

```powershell
# 1. Virtualización de firmware e hipervisor → AMBOS OK
Get-CimInstance Win32_Processor | Select Name, VirtualizationFirmwareEnabled
#   VirtualizationFirmwareEnabled : True   (SVM activado en BIOS)
(Get-CimInstance Win32_ComputerSystem).HypervisorPresent
#   True

# 2. WSL → NO INSTALADO
wsl --status
#   El Subsistema de Windows para Linux no está instalado.
#   Para instalar, ejecute "wsl.exe --install".

# 3. Servicios de virtualización → NINGUNO EXISTE
foreach ($s in 'vmcompute','hns','WslService','LxssManager') { ... }
#   vmcompute: NO EXISTE      (Hyper-V Host Compute Service — lo provee Virtual Machine Platform)
#   hns: NO EXISTE
#   WslService: NO EXISTE
#   LxssManager: NO EXISTE

# 4. Características de Windows (elevado) → YA ESTABAN Enabled, pero sin efecto
Get-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform
#   VirtualMachinePlatform  Enabled     ← habilitada en la base de datos de componentes,
#   Microsoft-Windows-Subsystem-Linux  Enabled     pero NUNCA se completó con reinicio
```

**Causa raíz compuesta**: las features de Windows estaban habilitadas "en papel" pero la máquina
nunca reinició para activarlas, el paquete moderno de WSL (MSIX/MSI) no estaba instalado, y el
instalador integrado `wsl.exe` de esta build está roto (ver bugs). Docker Desktop, al no poder
crear su utility VM vía WSL2, reporta el error genérico y equivocado de "virtualización".

## Bugs encontrados

### B1. Docker Desktop 29.8: mensaje de error engañoso
"Virtualization support not detected" cuando el problema real era WSL2 ausente. La frase
"Sign in to try restoring access" (upsell de licencia) mezclada en el error confunde más.
**Lección**: ante este error, verificar WSL/servicios ANTES de tocar BIOS.

### B2. `wsl.exe` stub roto en build 26200
`wsl --install --no-distribution` (y con `--web-download`, dentro y fuera del sandbox) solo imprime
"El Subsistema de Windows para Linux no está instalado…" y termina **sin hacer nada y sin lanzar UAC**
(exit 1). Probado 3 veces. **La vía que funciona**: DISM/`Enable-WindowsOptionalFeature` + MSI directo.

### B3. `Get-WindowsOptionalFeature -FeatureName` no acepta arrays
`-FeatureName A, B` falla con error terminante de binding
("No se puede convertir 'System.Object[]' al tipo 'System.String'"), que abortó el primer script
elevado **antes** de ejecutar los `Enable-*`. Llamar una feature por invocación.

### B4. `Write-Output` en script elevado se pierde
El script corre en una consola PowerShell elevada que se cierra al terminar: toda la salida de
`Write-Output` se pierde y el log queda vacío (exit 0 engañoso). **Usar `Start-Transcript`** dentro
del script, que sí captura todo al archivo.

### B5. Nombres de assets en WSL releases cambiaron
En la release 2.7.14 ya no existe `wsl.*.x64.msix` (el regex viejo no encuentra nada). Assets actuales:
- `wsl.2.7.14.0.x64.msi` — 247 MB ← **instalador recomendado** (machine-wide, `msiexec /qn`)
- `Microsoft.WSL_2.7.14.0_x64_ARM64.msixbundle` — 495 MB (Store, x64+ARM64)
- `wsl.2.7.14.0.arm64.msi`

### B6. Feature "Enabled" ≠ activa
`Enable-WindowsOptionalFeature` devolvió `RestartNeeded: True` sobre features que ya estaban
Enabled. Mientras `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPending`
exista, los componentes de virtualización no existen de verdad (servicios ausentes) aunque la feature
diga Enabled. **El reinicio es parte del fix, no un extra.**

## Fix aplicado (en orden)

1. **Script elevado con transcript** (`Start-Process powershell -Verb RunAs -Wait -PassThru` desde
   Git Bash, con `dangerouslyDisableSandbox` porque el sandbox bloquea el UAC). Dentro del script:
   `Start-Transcript -Path <log> -Force` para capturar todo.
2. **Habilitar features** (idempotente): `Enable-WindowsOptionalFeature -Online -FeatureName
   Microsoft-Windows-Subsystem-Linux -All -NoRestart` y lo mismo para `VirtualMachinePlatform`.
3. **Descargar WSL 2.7.14** desde la API de GitHub (asset `wsl.*.x64.msi`) con `Invoke-WebRequest`
   y **instalarlo silencioso**: `msiexec /i wsl.2.7.14.0.x64.msi /qn /norestart` → ExitCode 0.
4. **Verificar**: `wsl --version` → WSL 2.7.14.0, kernel 6.18.33.2-2, WSLg 1.0.73.2. `WslService`
   aparece como servicio (Stopped, normal hasta primer uso).
5. **Reiniciar Windows** (humano) para completar la activación de Virtual Machine Platform.
6. **Verificación final**: Docker Desktop arranca con engine en verde (confirmado por el usuario).

## Verificación post-reboot (comandos de control)

```bash
docker info                 # debe mostrar sección "Server:" (engine arriba)
wsl --version               # WSL 2.7.14.0
wsl --status                # sin errores de virtualización
powershell -NoProfile -Command "Get-Service vmcompute, WslService"   # Running
```

## Notas

- No se instaló ninguna distro Linux: Docker crea las suyas (`docker-desktop`). Si se quisiera
  Ubuntu para otra cosa: `wsl --install -d Ubuntu`.
- El botón "Sign in" de Docker Desktop es opcional (uso personal).
- Los temporales del fix (MSI 247 MB, script, log) se borraron tras la instalación.
- Nota: los comandos que instalan van con
  `dangerouslyDisableSandbox: true` y UAC real del sistema.
- Los comandos largos (descarga ~11 min a ~340 KB/s) pueden moverse a background del harness;
  esperar con TaskOutput.
